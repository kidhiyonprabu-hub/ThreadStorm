Theoretical & Empirical Performance Analysis

In a single-threaded server, each connection suffers from sequential blocking (head-of-line blocking). While the CPU executes socket reads and file I/O for client #1, clients #2-#100 stall in the kernel backlog. In ThreadStorm's multithreaded pool, 4 separate OS threads utilize multi-core parallelism, enabling concurrent request processing and drastically slashing total job completion time.

💡 Deep Dive Explain Mode
Under the hood mechanisms: Operating system concurrency & Winsock internals

Q1: Why is a request waiting in the bounded queue?

When incoming HTTP request bursts exceed the active worker capacity (e.g., 20 client connections arrive simultaneously while all 4 worker threads are currently serving sockets), the listener thread enqueues client sockets into the FIFO queue. If the queue reaches capacity (64 slots), ThreadStorm applies back-pressure and safely drops new connections to protect process memory.

Q2: How does a worker thread wake up without spinning?

Instead of busy-waiting (which would consume 100% CPU on all cores), ThreadStorm uses Windows Condition Variables:

// Worker waits in kernel sleep: while (q->count == 0 && !q->shutdown) { SleepConditionVariableCS(&q->not_empty, &q->lock, INFINITE); } // Accept thread signals upon new socket: WakeConditionVariable(&q->not_empty);

Q3: Why are CRITICAL_SECTIONs used instead of global mutexes?

A Windows CRITICAL_SECTION is a user-mode synchronization primitive with kernel fallback. Unlike a kernel HANDLE mutex, entering an uncontended critical section executes in user space via fast atomic instructions (under 10 nanoseconds) without triggering an expensive kernel transition context switch.

Q4: How does Canonicalization prevent Directory Traversal?

An attacker sending GET /../../windows/system.ini attempts to escape the public/ folder. ThreadStorm uses Windows GetFullPathNameA() to resolve all .. segments into an absolute path, then verifies that the resolved path strictly begins with the root public directory prefix. Any mismatch triggers an immediate 403 Forbidden and logs a security event.

Top College Viva Questions & Model Answers

Q1: What is a data race, and how does your Race Condition Arena prove it?

Answer: A data race occurs when two or more concurrent threads access a shared memory location simultaneously without synchronization, and at least one access is a write. In our Race Arena, multiple threads execute counter++ (which compiles into 3 assembly instructions: READ, MODIFY, WRITE). Because these instructions interleave unpredictably across CPU cores, updates are overwritten and lost. When wrapped with EnterCriticalSection(), atomicity is guaranteed and the counter reaches 100% of its expected value.

Q2: What are the four Coffman conditions for Deadlock, and how is it prevented here?

Answer: The four conditions are: (1) Mutual Exclusion, (2) Hold and Wait, (3) No Preemption, and (4) Circular Wait. ThreadStorm breaks the 4th condition (Circular Wait) by enforcing a strict linear lock hierarchy: all threads must acquire Resource A before Resource B. Since no thread can hold B while waiting for A, a circular dependency cycle is mathematically impossible.

Q3: Why is a thread pool superior to creating a new thread per request?

Answer: Spawning a new OS thread for every incoming connection incurs massive kernel overhead: 1 MB default stack allocation, context switching overhead, and thread creation latency (~1-2 ms). A thread pool pre-allocates a fixed number of reusable threads that stay alive, reducing latency to microseconds and preventing Out-Of-Memory crashes under high load.
